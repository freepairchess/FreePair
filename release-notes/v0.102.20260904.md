# FreePair v0.102.20260904

## Please upgrade

**This release completes a run of fixes for bugs that could corrupt your event
file. Upgrade before your next event, and take one minute to check any event
you have already run.** If you are on macOS (Intel) this is the first build in
that run to reach you.

FreePair edits your `.sjson` file in place: it changes the fields it manages
and leaves everything else exactly as it found it, so that details FreePair
does not display still survive a save. To do that it has to know which row is
which player, and which section is which — and until this run of releases it
worked that out from things that move. Players were identified by their seed
number, which re-seeding changes by design. Sections were identified by their
name, which renaming changes.

The consequence was that ordinary actions — re-seeding a roster before round
1, editing a rating, adding a late entry, renaming a section — could write a
player's details onto the row next to them. The most serious form of this
moved US Chess, FIDE, CFC and NWSRS ID numbers onto the wrong players.
**The US Chess ID is the identity a rating report is submitted under**, so an
affected event could have reported games against the wrong member numbers.

**What to do:** open any event you have run recently, look at a few ID numbers
on the Roster tab against the players they belong to, and save. Saving with
this build writes each player's own details back where they belong. It cannot
repair an event that was already saved wrong under an older build, because the
incorrect values are what the file now contains — which is why it is worth
checking before you submit.

## What's new

**Refresh Ratings now tells you it worked.** Every rating FreePair checked
against the current supplement gets a green check beside it on the Roster, the
same way a verified ID does. Most of the time nothing needs correcting, and
that is the answer worth showing: a column of green checks means the roster is
on the current supplement. Hover any of them to see whether the rating was
already right or was just corrected, and by how much.

Ratings FreePair could not check are simply left blank — no check, no warning
colour. A player with no ID yet, or one the rating database has no record of,
is not a problem and does not need flagging on the roster. The summary at the
end still lists them with the reason.

**Pressing Refresh Ratings always refreshes.** On an event where a quick
preliminary check saw no differences, FreePair used to show a message saying
everything already matched and stop there — no progress, no confirmation, and
nothing on the roster to show for it. That preliminary check only ever looked
at the first rating column, so on a dual-rated event it had not examined the
second one at all. The button now always performs the full check, against
every rating column, and shows you the result.

**NWSRS ratings refresh on files without rating-system labels.** On some
NWSRS events every ID showed a verified green check and the refresh then
reported "ID not verified — run Verify IDs first" for a player, which was
impossible advice: the IDs had been verified. FreePair now recognises the
NWSRS column consistently, whether or not the file labels it, and refreshes
those players normally.

**The progress window stays visible long enough to read.** A refresh over a
good connection can finish in a fraction of a second, and the window used to
appear and vanish faster than the eye could follow — leaving TDs unsure
whether anything had run.

**Sections keep their own identity, the way players already do.** Each section
carries a permanent, invisible identifier. Renaming sections — including
swapping two names, which used to trade their contents — no longer moves
anything between them. Deleting a section and reusing its name no longer
leaves a stale copy behind.

**Everything on a player's row travels with the player.** Re-seeding, rating
edits, late entries and deletions no longer leave IDs, ratings or other
details behind on the row — including details FreePair does not itself
display, such as age, which matters for age-prize eligibility.

**Deleting a player deletes the right one.** Since everyone below a removed
player is renumbered, the removed player's seed number instantly belonged to
somebody else. Removal now follows the player, not the number.

## Installer

Windows x64, macOS (Apple silicon and Intel) and Linux x64. The installer
bundles the .NET runtime, the pairing engines and the user guide — nothing
else to install. Run it and FreePair updates in place, keeping your events,
settings and recent-events list.

## Compatibility

The section identifier is stored under a `FreePair …` key, the same kind
FreePair already uses for its own settings. SwissSys and NA Chess Hub ignore
keys they do not recognise, so files continue to open in all three. Older
FreePair builds ignore it as well.

Existing events pick it up automatically the next time FreePair saves them.
There is nothing to configure.

## Known limitations

**An event already saved wrong cannot be repaired automatically.** FreePair
writes correct data from this build onward, but it has no way to know what an
already-corrupted file should have contained. This is why the check above is
worth a minute.

**Rating checks need the event linked to a rating database.** A player with no
ID, or an ID the database has no record of, cannot be checked and is left
unmarked rather than guessed at.

**Ratings are never changed for you.** Every difference FreePair finds is
reported; applying it is always your decision.

**Pairing fidelity.** FreePair's USCF engine is validated against a large
real-world SwissSys corpus and reproduces the great majority of pairings
exactly, reaching 100% on many representative events. The remaining
differences are in areas where the rules leave the director discretion —
board ordering within a score group, and which player receives a bye when more
than one is equally eligible. They do not affect the legality of a pairing.
